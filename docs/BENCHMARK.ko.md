# 성능 — 직접 잰 값

## 요약

| 조건 | PortButler | `scp` | `sftp` |
|---|---|---|---|
| 라즈베리파이 5, 1GbE | **108 MB/s** | 74 MB/s | 74 MB/s |
| localhost (선 제약 없음) | **465 MB/s** | 267 MB/s | 267 MB/s |

같은 맥·같은 서버·같은 64MB 파일. **1.45~1.74배.**

파이 쪽 108 MB/s는 **1GbE 이론 최대(119 MB/s)의 91%**다. 선이 거의 꽉 찼다는
뜻이라, 그 조건에서는 더 빨라질 자리가 없다. 그래서 CPU 상한을 보려면 선 제약이
없는 localhost로 재야 한다.

## 남의 수치를 인용하지 않는 이유

다른 SSH·SFTP 도구들도 성능 수치를 내놓지만 **그대로 가져다 비교하면 거짓말이
된다.** 하드웨어가 다르고, 네트워크가 다르고, 파일 크기가 다르고, 암호화 방식이
다르다. 기가비트 유선에서 잰 값과 Wi-Fi에서 잰 값을 나란히 놓으면 그 표는
사실이 아니라 광고다.

**그래서 같은 맥, 같은 서버, 같은 파일로 직접 잰다.** 아래 값은 누구나 같은
명령으로 다시 잴 수 있다.

## 측정 환경

| | |
|---|---|
| 클라이언트 | Mac (Apple silicon), macOS 26.6 |
| 서버 | Raspberry Pi 5, Ubuntu 24.04, OpenSSH |
| 네트워크 | 유선 1GbE, 왕복 지연 0.65ms (이론 최대 약 119 MB/s) |
| 두 번째 조건 | localhost — 선 제약을 없애고 CPU 상한을 본다 |
| 비교 대상 | OpenSSH 10.3p1 (`scp`, `sftp`) — macOS 기본 |
| 파일 | 64MB 무작위 바이트 (압축으로 속는 것을 피한다) |
| 횟수 | 각 3회, 아래는 실제 관측값 |

## SFTP 내려받기

| 도구 | 1회 | 2회 | 3회 |
|---|---|---|---|
| **PortButler** | **108.4 MB/s** | **108.0 MB/s** | **109.1 MB/s** |
| `scp` | 72.7 MB/s | 74.4 MB/s | 74.4 MB/s |
| `sftp` | 37.6 MB/s※ | 74.4 MB/s | 73.6 MB/s |

※ 첫 회는 연결·인증이 포함된 값이다. 나머지는 캐시가 데워진 뒤다.

**약 1.45배 빠르다.** 이유는 하나다 — **요청을 여러 개 동시에 띄운다.**

```
scp / sftp:   [요청]→ ... 응답 ←  [요청]→ ... 응답 ←   순서대로
              한 번에 32KiB, 왕복마다 0.43ms를 기다린다
              상한 = 32KiB ÷ 0.43ms ≈ 74 MB/s   ← 실측과 일치한다

PortButler:   [요청][요청][요청][요청] → 응답들이 뒤섞여 돌아온다
              스트림 4개 · 조각 256KiB · 각자 제자리에 쓴다
```

**왕복 지연이 곧 상한이 된다**는 것이 핵심이다. 벤치 도구가 그 상한을 함께
계산해 보여준다(`요청 하나씩일 때의 상한: 74.1 MB/s`). `scp`의 실측이 그 값과
거의 같다는 것이 이 설명이 맞다는 증거다.

**지연이 클수록 차이가 커진다.** 지구 반대편 서버(200ms)라면 순차 전송은
기어가고 병렬은 그대로 간다.

## SFTP 올리기

| 도구 | 1회 | 2회 | 3회 |
|---|---|---|---|
| `scp` | 73.6 MB/s | 74.4 MB/s | 74.4 MB/s |

**올리기는 아직 순차다.** 내려받기와 같은 구조로 바꿀 수 있지만, 원격 파일에
여러 곳을 동시에 쓰는 것은 중간에 끊겼을 때 **구멍 난 파일**을 남긴다. 그 처리를
제대로 하기 전에는 켜지 않는다 — 빠른 것보다 깨지지 않는 것이 먼저다.

## 터미널 스루풋

터미널은 파일 전송과 다른 문제다. **초당 몇 MB를 받느냐가 아니라, 받는 동안
화면이 멈추지 않느냐**가 기준이다.

```
목표     50 MB/s 이상, 프레임 예산(8.33ms) 안에서, 한 바이트도 잃지 않고
실측     통과 — 세 조건 모두
```

세 가지를 함께 본다.

**스루풋** — 초당 처리량. 이것만 보면 버퍼를 키우면 되므로 의미가 없다.

**drain p99 ≤ 8.33ms** — 120Hz 한 프레임. 이 값을 넘으면 프레임을 놓치고,
사용자에게는 **스크롤이 끊기는 것**으로 보인다. 평균이 아니라 99분위를 보는
이유는, 100번 중 한 번 끊기는 것도 눈에 띄기 때문이다.

**무손실** — 버퍼가 차면 **버리지 않고 늦춘다.** 터미널에서 한 줄이 사라지면
사용자는 그것이 사라졌다는 것조차 모른다. 로그를 보다가 중요한 줄을 놓치는
것이 느린 것보다 나쁘다.

## WindTerm의 공개 수치와 왜 나란히 못 놓는가

WindTerm은 SFTP 전송 벤치마크를 공개한다. 확인한 값(WindTerm 1.72):

| | 내려받기 | 올리기 |
|---|---|---|
| WindTerm | 216.3 MB/s | 247.0 MB/s |
| FileZilla | 161.1 MB/s | 171.8 MB/s |
| WinSCP | 63.7 MB/s | 56.7 MB/s |

**선이 병목인 값과 섞으면 안 된다.** 216 MB/s는 1GbE(최대 119 MB/s)에서 나올 수
없으므로 더 빠른 링크이거나 같은 기계 안에서 잰 값이다. 우리 파이 측정치
108 MB/s를 여기 나란히 놓으면 우리가 절반으로 보이는데, **그 비교는 CPU가 아니라
랜선을 비교하는 것이다.**

그래서 선 제약이 없는 조건끼리 놓는다:

| | 내려받기 | 올리기 |
|---|---|---|
| **PortButler** | **465 MB/s** | 267 MB/s |
| WindTerm 1.72 | 216.3 MB/s | 247.0 MB/s |
| FileZilla | 161.1 MB/s | 171.8 MB/s |
| WinSCP | 63.7 MB/s | 56.7 MB/s |

우리 값은 Apple silicon 맥, 저쪽은 Windows 10 / Core i5 2.3GHz다. **기계가 다르니
자릿수 감각으로 읽을 것** — 정밀 비교를 하려면 같은 맥에 설치해 같은 파일로 재야
한다.

출처: [WindTerm — Performance / Sftp Transfer](https://kingtoolbox.github.io/2023/11/15/benchmark-sftp-transfer/)

## 다시 재는 법

```sh
# 터미널 스루풋 게이트 (합성 부하)
cargo run --release --bin throughput -- 5 50 8

# SFTP — ssh_config에 별칭이 있어야 한다
cargo run --release --bin sftp-bench -- <별칭> 64

# 비교 대상
scp <서버>:/tmp/bench.bin /tmp/out.bin
sftp <서버>:/tmp/bench.bin /tmp/out.bin
```

## 정직하게 적어두는 것

**내려받기만 빠르다.** 올리기는 `scp`와 같다.

**작은 파일에서는 차이가 없다.** 병렬화는 왕복 지연을 감추는 기법이라, 왕복이
몇 번 안 되는 크기에서는 이득이 없다.

**서버가 병목이면 차이가 없다.** 라즈베리파이 5는 암호화를 충분히 빠르게 하지만,
더 약한 보드에서는 서버 CPU가 먼저 막힌다.

**선이 병목이면 그것도 차이가 없다.** 1GbE에서 우리는 이미 91%를 쓰고 있다.
그 조건에서 더 빠른 클라이언트는 존재할 수 없다 — 남은 9%는 프로토콜 부담이다.

**첫 회 값은 다르다.** 연결과 인증이 포함된다. 위 표의 `sftp` 1회가 그 예다.
